Fast cores, slow growth, capped writes

A measured profile of the Anthropic-cloud microVM behind this Claude Code session — four dedicated Cascade Lake vCPUs that scale perfectly, a one-time memory tax of 5.5 s per gigabyte, and a disk that reads 14× faster than it writes.

Scope. The client device — an Android handset — exposes no telemetry to this session; the only thing reported about it is the string android. Everything below measures the remote Linux microVM where code actually executes, which is what governs how fast work runs.

Gap — no SHA extensions

sha_ni is absent from the CPU flags, so SHA-256 runs in software at 395 MB/s single-threaded where the hardware path would give roughly 2 GB/s. AES-NI is present and delivers 1.16 GB/s on AES-256-CBC.

This taxes git object hashing, checksum verification and container-layer work by about 5×. It is a property of the host CPU model, not something tuning can fix.

Root cause

The first time a process grows into fresh memory, the hypervisor populates host backing on demand — roughly 5.5 seconds per gigabyte of new resident set. Once the guest kernel holds those pages, re-faulting them costs 1.4 µs and access runs at the full 23 GB/s.

Compounding it, transparent_hugepage is set to [madvise], so huge pages are off unless a program asks. That is why random access measures 151 ns — TLB-miss heavy on 4 KiB pages — and why fault counts stay high.

In practice: a large first build, a dataset load, or a heavy Node/JVM heap stalls for several seconds with no output. That is memory population, not a hang. It does not repeat.

Git on the working repository is effectively free — git status 2.5 ms, git log -50 2.3 ms, git diff HEAD 2.2 ms — though on a 304 KB checkout that measures process startup more than git itself.

Network — two different paths

Bulk download reached 62 MB/s. TLS handshake runs ~85 ms and TTFB to the GitHub API settles at 119–149 ms after a 321 ms cold first call. DNS is locally cached at ~0.02 ms.

Package registries — registry.npmjs.org, pypi.org, files.pythonhosted.org, index.crates.io, proxy.golang.org — sit in the proxy's noProxy list and go direct. GitHub API traffic is proxied and carries the full round trip.

Actions

What to do with this

  1. Budget 30 GiB, not 252 GiB.
    df advertises a 252 G device but the session allowance is 30 G. This is the most likely real failure — a deep clone or a large node_modules tree hits it before anything else does.
  2. Expect one slow pass, then speed.
    A first build that stalls for several seconds with no output is the memory-population tax at 5.5 s/GB. Don't kill it — it never repeats.
  3. Parallelize freely — -j4 is honest.
    Unlike burst-credit VMs, sustained four-core load costs nothing here. Scaling measured 3.99× with zero steal.
  4. Avoid write-amplifying steps.
    Prefer git clone --depth, skip large intermediate artifacts, and pipe rather than staging through disk. 170 MB/s is the floor you will hit.
  5. Ask for huge pages in numeric code.
    madvise(MADV_HUGEPAGE) would meaningfully cut the 151 ns random-access latency. THP will not engage on its own at this setting.
Measured on an idle container — load average 0.08, one minute after boot. Under concurrent load the CPU figures divide as expected; the disk write cap and the memory fault tax are structural and will not improve.
Tools: hand-written C (gcc -O2), OpenSSL speed, dd, Python timing harnesses, curl, vmstat. sysbench and fio were unavailable.
